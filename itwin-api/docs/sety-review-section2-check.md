# Раздел 2 обзора sety — проверка на данных (29.10.2026)

Обзор: `sety/REVIEW_2026-10-18.md`, раздел 2 «Подозрительные места — проверить на данных».
Код sety не менялся: проверка — эталонные расчёты (`docs/sety-golden-reference.md`) и зонды
`scripts/golden/sety_probe.py`. Зонды подменяют функцию так, как предлагает обзор, после чего
снимок сравнивается с эталоном. Правки здесь — **предложения автору sety**.

Данные: Алматы 74 (плановый и фактический `-a`), Алматы 72 (плановый), Tн −20, `almatygid_copy`;
Шатура 3252 (плановый, Tн −25, `shatura_copy`); Астана 3179 (плановый по ТГ `-tg`, Tн −31,2,
`astanagid_copy` — копия от 29.10). Код sety — ветка `modernization/phase-0`
(поставки до 27.10 включительно, отпечаток `9f144045a3dc`). В Шатуре тепловой расчёт не идёт
(«тепловой расчет не производится» у всех 8 подсетей), поэтому выводы по температурам — по Алматы.
Зонды гонялись на Алматы и Шатуре. По Астане разобран эталонный расчёт: протокол, `rs_out`,
`ns_out`, `any_out`.

## Подробно

### 2.1. `read_row`/`read_row2` отбрасывают 0

Зонд `count` насчитал отброшенные нули: Алматы 74 — 45 тыс. значений, 72 — 89 тыс., Шатура —
68 тыс. Почти все — нулевые нагрузки и расходы потребителей, у которых умолчание тоже 0. Нули с
ненулевым умолчанием, которые встречаются в данных:

- `realConsumers.calcTempHWDO` (температура горячей воды, `Tr_gvs`, умолчание 60): в Шатуре
  0 у 762 из 1112 потребителей — sety молча считает 60 °C;
- `realConsumers.mixFactCoeff` (коэффициент смешения): 0 у 389 потребителей 72, 279 — Шатура;
- `heatSources.*` (летние температуры, `q_r`, `uf` и т. д.) — нули у 50–130 источников.

Зонд `keep_zeros` (нули сохраняются) не изменил ни одного числа ни в одном случае: при этих
данных умолчания совпадают с поведением при нуле или поле не используется в выбранном режиме.
**Вывод:** на эталонах не влияет. Риск остаётся для данных, где ноль означает «0», а умолчание
другое. Предложение автору: брать `v is not None`, а подстановку умолчания делать явно и с
предупреждением, как уже сделано для диаметра и длины (п. 2.1 в `read_gid.py`).

Попутно по данным: в Алматы 72 у 40 потребителей `calcTempHWDO` = 1 °C, у 3 — 160 °C. Это
ошибки ввода, их стоит показать в проверке данных фрагмента (`check_fragment.py`).

### 2.2. Коэффициенты вариации по умолчанию 0

Зонд `kv1` подставляет 1 вместо незаполненного коэффициента. В Алматы 74 у 9 из 10 групп
коэффициентов `gvoo` = 0 (не заполнен), у одной не заполнены `kondiz`, `txz`, `txop`, `txoo`, `gvz`.
Нагрузка, которая действительно обнуляется, — одна: потребитель «Ябл РСюс» (узел 536374) с ГВС
из обратки. Требуемая нагрузка 0,0048 Гкал/ч (с коэффициентом 0 — ноль), расход +0,036 т/ч,
b106 на пяти участках к ТЭЦ-1 +0,002 Гкал/ч, у 4 регуляторов давления меняется состояние
(«открыт» ↔ «рабочее»). Так и в плановом, и в фактическом режиме. В 72 и Шатуре изменений нет
(в 72 одна группа без пропусков, в Шатуре задан общий `kvpot`).
**Вывод:** подтверждается, влияние на этих данных малое. Предложение: умолчание 1 для
незаполненного коэффициента (0 — только явно заданный) и предупреждение в протоколе.

### 2.3. «Поправка на подпитку» температуры (`out/us_out.py`: `t = -t*Gout/Gin`)

Зонд `no_podpitka_t` убирает поправку. Поправка срабатывает у 2 узлов в Алматы 74 и у 105 в 72;
температура в `us_out` меняется:

| узел | с поправкой (пишется) | без поправки (расчёт) |
|---|---|---|
| 72: «РС1-7 10-1» О | 24,98 | 49,26 |
| 72: «РС1-7 13-41» О | 56,73 | 30,77 |
| 72: «13А-2 МТК13А-5» О | 56,22 | 38,78 |
| 74: «6-8 ЦТРП» О | 57,79 | 50,03 (факт. режим — до 16 °C) |
| 74: «РС1 ТЭЦ-1» О | 57,36 | 52,97 |

Поправка сдвигает температуру в обе стороны и до 26 °C. Смешение с холодной подпиткой не может
поднять температуру, а утечка температуру не меняет вовсе. Поправка влияет только на записанную
`us_out.t` (тепловой расчёт её не использует): карта и пьезометр показывают одно, а расчёт
потребителей — другое.
**Вывод:** подтверждается. Предложение: писать расчётную температуру узла; если нужна температура
смеси с подпиткой — считать её смешением (Σ G·t / Σ G) с температурой подпиточной воды. То же
место в `out_teplo.protocol_IS_OUT` и `is_out` (`t2_ispr *= Gin_P/Gin_O`) — только протокол.

### 2.6. `teplo/tepl_gws1ps.py`: `getE1` и умолчания `Tx`

### 2.7. `dross/drvary5.py`: две формулы `hrc`

`realConsumers`/`generalizedConsumers` и меняет исходные данные копии для следующих расчётов.
В эталоны не включён. **Не проверено.** Для проверки нужна отдельная одноразовая копия базы.

### 2.8. `teplo/y_ut.py`

- `-trtp` перекрыт `Tn = t_or`: `check --set trtp=1` по Алматы 74 и 72 дал «совпадает» с эталоном
  (`-trtp 0`) — флажок «Температура расчёта тепловых потерь» на результат не влияет.
  **Подтверждается.** Строка оставлена автором намеренно, «как в десктопе», до его решения; по
  прежней проверке без неё температуры узлов 74 в среднем +0,76 °C (до +16 °C на концах обратки).
  Решение — за автором sety: либо убрать перекрытие, либо убрать флажок из интерфейса.
- Справочник 39 (база `sprav`, 576 строк): автор уже сортирует строки по диаметру
  (`rows = sorted(...)`), то есть порядок `SELECT` не важен. В таблице каждая строка задвоена
  (288 пар `date/proklad/диаметр`, различаются только `mode` NULL/1), нормы в парах одинаковы —
  сейчас не влияет. Если пары разойдутся, победит последняя прочитанная.
- «300 при отсутствии таблицы»: на эталонах `get_q_new` вызван 7480 (74) и 20960 (72) раз, 300 —
  ни разу.

### 2.9. `w_out.py`

- `set_RD_out`: `delta0 = 1` вместо `delta`. В Алматы 74 — 65 регуляторов давления
  (`pressRegulators`: у 111 из 151 по фрагменту delta < 1, у 23 — 0). По `rs_out` ни у одного
  работающего РД отклонение не попало между заданной точностью и 1 м — подавленных
  предупреждений на этих данных нет. Риск остаётся: при delta 0,1–0,5 отклонение до 1 м молчит.
  Астана 3179: 32 РД, единственный с отклонением между delta и 1 м («0 У654989955 – 0 У654989953»,
  задано 85, получено 84,32, delta 0,01) работает в реверсе, и про реверс sety предупреждает.
  Подавленных предупреждений нет.
- `set_HC_out`: у насоса с заданным напором (`h > 0`) «перегруз» не определяется. В Алматы 74 —
  37 насосов, ни один не работает сверх `qmax`. **В Астане 3179 подтверждается:** у 81 из 106 насосов
  задан напор, и 10 из них работают сверх `qmax` (например, «НС-5» «0 У321322098 – 0 У321322099»:
  3333 т/ч при `qmax` 2760, напор 110 м). Протокол пишет «превышает его пропускную способность»,
  а в `ns_out.a17` у них «рабочая», так что веб (журнал насосов, карточка) показывает норму.
Предложение: убрать отладочную строку `delta0 = 1`; перегруз проверять по `qmax` независимо от `a3`.

### 2.10. `w_print.node_names`

Для узла внутренней схемы ссылка ведёт на узел-владелец. Веб на это рассчитывает: в
`utils/calc_protocol.py` указано «для узлов внутренней схемы — узел-владелец», а внутренние
узлы на карте не показываются (в Алматы 74 их 392). После `setG` имена берутся из полного графа
— тоже намеренно: в подсети нет всех узлов. **Менять не нужно.**

### 2.11. `config.get_args_json`

В `calculation.calc_params` всех эталонных расчётов нет `sopr`, `no_kv`, `GWS`, `GWS2`, `is_plan`
(режим виден только по `g_is_avar`). Ключи `n_GWS`, `n_GWS2`, `is_kv` из списка `allowed` не
появляются: таких аргументов нет. **Подтверждается.** Без этих полей по `calc_params` не повторить
расчёт и не понять, учитывались ли коэффициенты вариации.
Предложение: заменить в `allowed` `n_GWS`/`n_GWS2`/`is_kv` на `GWS`/`GWS2`/`no_kv` и добавить `sopr`, `roP`, `roO`.

### 2.12. Регуляризация `DIAG_REG = 1e-6`

- Тепловой расчёт (`teplo1.init_matrix_teplo`): зонд `diag_reg_off` вычитает добавку перед
  решением (6 систем на 74, 333 на 72). Температуры обычных узлов меняются не больше чем на
  0,0007 °C (74) и 0,0036 °C (72) при допуске 0,05 °C. Сдвиг решения есть, но на этих данных
  пренебрежимо мал.
- Нагрузки (`calc_nagr`): автор 22.10 перенёс добавку в `regularize()` — только если матрица не
  раскладывается. Зонд `count`: запасной вариант срабатывает 1 раз на 74 и 108 раз на 72. Зонд
  `nagr_reg_off` (добавка 0, нулевые диагонали → eps): b101–b106 совпали с эталоном точно,
  тождество b101 = b102+…+b106 держится на всех эталонах.
- Узлы без протока: регуляризация делает систему решаемой, но их температура остаётся
  бессмысленной (−10⁶…−10¹⁰ °C — см. «Попутные находки», п. 2). Без `DIAG_REG` у узла 525541
  (72) значение тоже около −3,5·10⁹. Дело не в величине добавки, а в том, что такие узлы пишутся
  в `us_out`.
**Вывод:** на эталонах не влияет. Предложение: добавлять регуляризацию только к узлам без протока
(или исключать их из системы) и не писать их температуру.

### 2.13. Тепловой расчёт: 5 итераций

Автор 22.10 добавил выход по сходимости (`EPS_T_CALC = 0,01` °C). Зонд `teplo_iters`: Алматы 74 —
2 и 4 итерации, 72 — 176 вызовов, 2–4 итерации (40 подсетей без источника — 0), последняя
Δt ≤ 0,0037 °C. Предела 5 не достиг ни один вызов. Но если предел будет достигнут, расчёт молча
продолжится. Предложение: предупреждение в протоколе при выходе по пределу. Параметр `teploYes0`
по-прежнему ни на что не влияет (`teploYes = True` всегда).

### 2.14. `w_calc.solve_G`

По `stderr` (строки `iter:`): Алматы 74 — до 17 итераций, 72 — до 9, факт — до 22. Предела 100
нет, предупреждений о вырожденной матрице нет. Шатура: одна подсеть из 75 неизвестных дважды
проходит все 100 итераций, d падает медленно (0,106 → 0,0094) и выше критерия 0,001. Расчёт
продолжается молча. Критерий — сумма модулей приращений, на крупной сети он строже, чем на
малой, поэтому эффект «зависит от размера» здесь обратный ожидаемому.
**Вывод:** частично подтверждается: несходимость не сообщается. Предложение: критерий по
максимуму или норме, отнесённой к числу неизвестных, предупреждение при выходе по пределу,
проверка `isfinite` после `spsolve` в основном цикле (в `rd_newton` она уже есть).

Мелочь: в том же цикле переменная внешнего цикла `i` затирается внутренним
`for i in range(len(root))` и уходит в `w_rd.check_RD(..., i, ...)`. Там она используется только
в логе, на результат не влияет.

### 2.15. MS SQL

На данных не проверяется. По коду: `read_gid.read_node` — `ORDER BY n.internalNodeID is not null`,
`UPDATE … FROM` — синтаксис PostgreSQL. Умолчание `-rdbms` в `config.py` — `MsSql`, поэтому
запуск без явного `-rdbms` уйдёт в ODBC MS SQL. Веб и десктоп передают `postgreSQL`.
Предложение: умолчание `postgreSQL`; MS SQL пометить неподдерживаемым или убрать.

## Попутные находки (вне раздела 2)

1. **Граничные условия из чужого расчёта.** Узлы с заданным напором берут напоры, температуры и
   источник из ПОСЛЕДНЕГО расчёта фрагмента-магистрали (`setPressNodes.fragment_resultID`,
   `read_gid.py`). Алматы 72 берёт их у 110 узлов из последнего расчёта 74. Если последним 74
   посчитали при другой Tн или летом, 72 считается от чужих условий: подача 132 °C против
   121 °C, температуры и нагрузки у 2200 потребителей другие. Пользователь этого не видит.
   Предложение: писать в протокол номер и дату расчёта магистрали, предупреждать при другой Tн
   или режиме. Эталоны теперь сначала пересчитывают магистраль и сохраняют граничные условия.
2. **Мусорные температуры в `us_out`.** Фактический режим (`-a`), Алматы 74: 917 синтетических
   узлов (id < 0) с температурами −10⁶…−10¹⁰ °C, номера при каждом расчёте свои. Алматы 72
   (плановый): узел 525541 О — около −4·10⁹ °C. Это узлы без протока в тепловой матрице с
   регуляризацией (см. п. 2.12). Предложение: для узлов без протока писать NULL (или −10000, как
   для узлов вне расчёта), а не результат регуляризованной системы.
