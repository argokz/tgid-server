# Вебхуки и публичный API v2

Фаза 2 плана модернизации: внешние системы (ERP, биллинг, CRM, call-центр, 1С) узнают о событиях ТГИД сразу и
работают с нарядами, отключениями и дефектами через стабильный API.

- **Вебхуки** — ТГИД сам отправляет событие POST-запросом на адрес системы: новый дефект, новый наряд, смена
  статуса наряда, отключение запланировано или объявлено.
- **Лента событий** `/api/v2/events` — те же события для систем, которые не могут принимать входящие запросы
  (опрос раз в минуту).
- **API v2** — чтение нарядов, отключений и дефектов, создание заявки. Адреса v2 не меняются вместе с вебом:
  поля только добавляются, удаление и переименование — только в v3.

Код:
- API: `database/api_events.py` (журнал событий), `database/webhooks.py` (подписки и доставка),
  `routers/webhooks.py`, `routers/api_v2.py`, миграция `sql/migrations/20261030_webhooks.sql` (API применяет
  её сам — `city_schema`), тесты `tests/test_webhooks.py`;
- веб: «Администрирование → Вебхуки» (`components/WebhooksDialog.vue`), «Учётная запись → Ключ API v2»
  (`components/ApiKeyPanel.vue`), `utils/webhooks.ts`, тесты `tests/utils/webhooks.spec.ts`.

## События

| Тип | Когда | Данные (`data`) |
|---|---|---|
| `defect.created` | новая запись журнала дефектов — из веба, с обхода бригады или **из десктопа** | `defect_id`, `detected_at`, `category`, `state`, `source`, `line_id`, `lon`, `lat` |
| `work_order.created` | новая заявка или наряд (в том числе через API v2) | `work_order_id`, `number`, `kind`, `priority`, `status`, `defect_id`, `line_id`, `node_id`, `lon`, `lat`, `planned_finish` |
| `work_order.status_changed` | назначен, в работе, выполнен, **закрыт**, отменён, возвращён | то же и `from_status` |
| `outage.created` | запланировано отключение | `outage_id`, `number`, `kind`, `status`, `planned_start`, `planned_end`, `consumers_count`, `load_gcal_h`, `public`, `work_order_id`, `line_id`, `node_id` |
| `outage.status_changed` | объявлено, идёт, завершено, отменено | то же и `from_status` |
| `sensor.deviation` | датчик телеметрии: показание расходится с моделью (`docs/telemetry.md`) | `alert_id`, `sensor_id`, `code`, `name`, `kind`, `pipe`, `node_id` / `line_id`, `status`, `prev_status`, `value`, `model`, `unit`, `diff`, `pct` |
| `sensor.silent` | датчик молчит — нет показаний дольше 60 мин | то же |
| `sensor.recovered` | датчик вернулся в норму | то же |

Данные события — короткие и **без персональных данных**: без имён потребителей, логинов сотрудников и свободного
текста (в название и описание наряда call-центр может вписать телефон жителя). Подробности (название, зона
отключения, история, адрес дефекта) система берёт из API v2 своим ключом — с маскированием по правам этого ключа.

Как собираются: фоновая задача API раз в `WEBHOOK_POLL_S` секунд (по умолчанию 10) переносит новые записи истории
нарядов и отключений и журнала дефектов в `tgid_api_event`. Код нарядов и отключений о вебхуках не знает;
дефекты десктопа попадают в события, хотя десктоп ничего не отправляет. События до первого запуска API с этой
версией наружу не уходят. Журнал событий хранится 30 дней.

Тело события:

```json
{
  "id": "evt_almaty_48",
  "type": "outage.status_changed",
  "occurred_at": "2026-10-30T08:46:28Z",
  "city": "almaty",
  "data": { "outage_id": 8, "number": "О-2026-00008", "status": "active", "from_status": "announced", "…": "…" }
}
```

`id` — ключ события: повтор доставки приходит с тем же `id`, получатель отбрасывает уже обработанные. Порядок
доставки не гарантирован (повтор старого события может прийти после нового) — сортируйте по `occurred_at` и
номеру в `id`.

## Вебхуки

### Подписка

Администратор в «Администрирование → Вебхуки»: название, адрес, события. Секрет подписи показывается один раз
(и при «Новый секрет» — старый перестаёт действовать сразу). «Проверить» отправляет событие `ping` и показывает
ответ адреса. «Доставки» — журнал: состояние, число попыток, ответ; не доставленное можно отправить ещё раз.

Адрес — запрос с сервера API наружу, поэтому:
- только `https://` (http — если служба включила `WEBHOOK_ALLOW_HTTP=1`: 1С или ERP во внутренней сети);
- внутренние сети и localhost (10.x, 172.16–31.x, 192.168.x, 127.x, fc00::/7) — только при
  `WEBHOOK_ALLOW_PRIVATE=1`; link-local (169.254.x — адреса метаданных облака), CGNAT 100.64.0.0/10 (там адрес
  метаданных Alibaba Cloud), multicast, 0.0.0.0 и прочие не публичные адреса — никогда; IPv4 внутри IPv6
  (::ffff:…, 6to4, NAT64) проверяется как IPv4;
- порт — любой: администратор с `WEBHOOK_ALLOW_PRIVATE=1` может отправить POST на любой порт внутренней сети —
  включайте флаг, только если подписки ведут доверенные администраторы;
- адрес хоста проверяется при каждой доставке (все адреса из DNS), и запрос идёт на проверенный IP —
  подмена DNS между проверкой и запросом не проходит; сертификат проверяется по имени хоста;
- перенаправления (3xx) не выполняются — это неудачная доставка;
- тело ответа не читается, на всю отправку — не больше 15 с: медленный адрес не задерживает остальные доставки;
  прокси из переменных окружения службы (`HTTP_PROXY`) не используется.

### Запрос

`POST <адрес>`, `Content-Type: application/json`, заголовки по спецификации
[Standard Webhooks](https://www.standardwebhooks.com):

| Заголовок | Что |
|---|---|
| `webhook-id` | ключ события (`evt_…`) |
| `webhook-timestamp` | время отправки, секунды Unix |
| `webhook-signature` | `v1,` + base64(HMAC-SHA256(ключ, `«webhook-id».«webhook-timestamp».«тело»`)), ключ — base64 после `whsec_` в секрете |
| `user-agent` | `TGID-Webhooks/1` |

Получатель проверяет подпись по телу **как оно пришло** (до разбора JSON) и отклоняет запросы старше 5 минут.
Готовые библиотеки проверки есть для Python, Node.js, C#, Go, PHP, Java (`standardwebhooks`); код для Node.js —
в окне после создания подписки.

Ответ 2xx — доставлено. Любой другой ответ, нет ответа за 10 с или ошибка соединения — повтор через 1 мин,
5 мин, 30 мин, 2 ч, 5 ч, 10 ч, 10 ч (8 попыток, чуть больше суток), затем «не доставлено». Подписка, которая
не принимает ничего 3 дня, выключается сама («Выключена: адрес не принимает события 3 дн.»); «Включить» в окне
снова запускает её. Отвечать стоит сразу (до 10 с), а долгую обработку делать после ответа.

### Адреса API (администратор)

| Адрес | Что |
|---|---|
| `GET /api/v1/webhooks/event-types` | типы событий |
| `GET /api/v1/webhooks` | подписки с числом доставок |
| `POST /api/v1/webhooks` | `{name, url, events}` → подписка и `secret` (один раз); журнал действий `WEBHOOK_CREATE` |
| `PATCH /api/v1/webhooks/{id}` | `name`, `url`, `events`, `active` (`WEBHOOK_UPDATE`) |
| `DELETE /api/v1/webhooks/{id}` | удалить с журналом доставок (`WEBHOOK_DELETE`) |
| `POST /api/v1/webhooks/{id}/secret` | новый секрет (`WEBHOOK_SECRET`) |
| `POST /api/v1/webhooks/{id}/test` | событие `ping` сейчас: `{ok, code, error, ms}` |
| `GET /api/v1/webhooks/{id}/deliveries?status=` | последние доставки |
| `POST /api/v1/webhooks/deliveries/{id}/retry` | отправить ещё раз — не доставленную или ждущую повтора; отправляемую сейчас — 409 (`WEBHOOK_RETRY`) |

## API v2

Адрес — `<адрес API>/api/v2` (на API нескольких городов — `<адрес API>/city/<код>/api/v2`). Описание OpenAPI —
`/api/v2/openapi.json`: только адреса v2, по нему генерируется клиент (openapi-generator, NSwag для 1С/.NET).

### Ключ

Пользователь выдаёт ключ себе: «Учётная запись → Ключ API v2» (`POST /api/v1/api-key`). Ключ — заголовок
`Authorization: Bearer <ключ>`:
- действует только на `/api/v2` (остальное API его не принимает) — `API_TOKEN_DAYS` дней, по умолчанию 365;
- права — пользователя, выдавшего ключ: для интеграции заведите отдельного пользователя с нужными правами
  (чтение — любой вошедший, создание заявок — право «Журналы»); персональные данные маскируются, если у него
  нет права «Персональные данные»;
- закрывается сменой пароля и блокировкой пользователя; выдача — в журнале действий (`API_KEY`), действия по
  ключу — тоже, от имени пользователя;
- отдельный ключ отозвать нельзя: только сменой пароля (у пользователя PostgreSQL и мастер-учётки — блокировкой
  или сменой мастер-пароля) — так же, как ключи ArcGIS и MCP. Для интеграции заводите отдельного пользователя.

### Адреса

| Адрес | Что |
|---|---|
| `GET /api/v2` | версия, город, типы событий |
| `GET /api/v2/events?after=&types=&limit=` | лента событий после `after` (номер `seq` последнего полученного): `{data, next_after, has_more}` |
| `GET /api/v2/work-orders?status=&updated_since=&after_id=&limit=` | наряды и заявки |
| `GET /api/v2/work-orders/{id}` | наряд с историей статусов |
| `POST /api/v2/work-orders` | заявка: `{title, description, kind, priority, line_id \| node_id \| lon+lat, planned_finish}` → 201 |
| `GET /api/v2/outages?status=&updated_since=&after_id=&limit=` | отключения |
| `GET /api/v2/outages/{id}` | отключение с зоной (GeoJSON, WGS 84) и историей |
| `GET /api/v2/defects?after_id=&limit=` | журнал дефектов |
| `GET /api/v2/defects/{id}` | дефект |

Списки — по возрастанию `id`, до 500 за запрос: `{"data": [...], "next_after_id": N}`; следующая страница —
`after_id=N`, `null` — страниц больше нет. `updated_since` — изменённые с этого времени (синхронизация).
Время — ISO 8601 с часовым поясом. Ошибки — `{"detail": "…"}` с кодом HTTP (401 — ключ, 403 — права,
404, 409 — конфликт, 422 — запрос).

`POST /api/v2/work-orders` с заголовком `Idempotency-Key` (до 100 символов, например номер обращения в CRM):
повтор с тем же ключом от того же пользователя возвращает тот же наряд (200 и `Idempotent-Replayed: true`), а не
создаёт второй; два одновременных запроса с одним ключом тоже дают один наряд. Тот же ключ с другим названием
заявки — 422. Ключи разных пользователей не пересекаются (ключ действия — HMAC с секретом сервера). Без места
(`line_id`, `node_id` или `lon` и `lat`) — 422.

Синхронизация без вебхуков: опрашивать `/api/v2/events?after=<последний seq>` раз в минуту и по событиям
дочитывать объекты. Номер `seq` хранить у себя: события старше 30 дней удаляются.

## Настройки службы

| Переменная | По умолчанию | Что |
|---|---|---|
| `WEBHOOK_POLL_S` | 10 | как часто собирать события и отправлять доставки; 0 — выключить события и вебхуки |
| `WEBHOOK_ALLOW_HTTP` | выкл. | разрешить `http://` адреса подписок |
| `WEBHOOK_ALLOW_PRIVATE` | выкл. | разрешить адреса внутренней сети и localhost |
| `API_TOKEN_DAYS` | 365 | срок ключа API v2 (до 730) |

Несколько процессов API (или служб одного города) не мешают друг другу: сбор событий — под advisory-замком
базы, доставки забираются `FOR UPDATE SKIP LOCKED`. Серверу API нужен доступ к адресам подписок.

## Проверено (копия Алматы, 30.10.2026)

- Стенд: приёмник на `127.0.0.1:5601` проверяет подпись; API с `WEBHOOK_ALLOW_PRIVATE=1`, `WEBHOOK_ALLOW_HTTP=1`,
  `WEBHOOK_POLL_S=3`. Таблицы созданы доводкой базы при запуске.
- Подписка на все события → «Проверить» → ping принят, подпись верна. Наряд создан и отменён, отключение
  запланировано (19 потребителей, 57,2 Гкал/ч), объявлено → 4 события дошли за 1–8 с, подписи верны.
- Приёмник ответил 500 → доставка «повтор через минуту», у подписки — начало сбоев; через минуту то же событие
  (тот же `id`) доставлено со второй попытки, отметка сбоя снята.
- https на проверенный IP: локальный https-сервер с сертификатом на `tgid-hook.test` — запрос на 127.0.0.1 прошёл,
  сертификат проверен по имени, `Host` — имя хоста; сертификат на чужое имя — отказ.
- Адреса `https://169.254.169.254/…`, `ftp://…`, неизвестный тип события — 422.
- API v2: лента событий и фильтр по типу, наряд с историей, отключение с зоной, `updated_since`; заявка с
  `Idempotency-Key` дважды — один наряд (201, затем 200 и `Idempotent-Replayed`), без места — 422.
- В браузере: окно «Вебхуки» — список, «Проверить», журнал доставок (в том числе «попыток 2»), новая подписка
  с показом секрета и кода проверки.
- Тесты: `tests/test_webhooks.py` (14, в том числе пример подписи из спецификации Standard Webhooks),
  `tests/utils/webhooks.spec.ts` (4).
- Не проверено: доставка на настоящий внешний https-адрес (стенд не отправляет данные наружу), ключ API с
  включённым входом — только тестами.
