# Живая карта: присутствие и правки других пользователей

Фаза 2 плана модернизации, п. 11 раздела 2а («присутствие и живые правки», шаг 1). Несколько диспетчеров и
инженеров работают с картой одного города одновременно:
- видно, **кто сейчас на карте**, где смотрит и какой объект открыл на правку («Показать» — перелёт к его виду);
- **правки других** — в вебе, в десктопе или скриптом прямо в базе — видны на карте за 2–4 с (раньше — через
  30–60 с опроса версии данных) и коротким уведомлением «Изменения на карте — olga: узлы — 3»;
- в карточке правки объекта — предупреждение, если его **сейчас правит кто-то ещё**, и «Объект изменил … —
  значения в форме устарели. Обновить», если его сохранили, пока карточка была открыта.

Блокировки объектов нет: два человека могут открыть одну карточку, а сохранение второго покажет конфликт
версии (как и раньше — карточки сверяют версию строки). Живая карта предупреждает об этом заранее.

Код:
- API: `database/live.py`, `routers/live.py`, миграция `sql/migrations/20261031_live_presence.sql` (API применяет
  её сам — `city_schema`), тесты `tests/test_live.py`;
- веб: `stores/liveStore.ts`, `composables/useLiveChannel.ts` (запуск из карты), значок «Кто на карте» в верхней
  панели (`components/LivePresence.vue`), предупреждения в `components/objectCard/ObjectCardEdit.vue`, разбор
  потока `utils/liveStream.ts`, тесты `tests/utils/liveStream.spec.ts`.

## Как устроено

**Поток событий, а не WebSocket.** Браузер держит `GET /api/v1/live/stream` — Server-Sent Events: обычный HTTP-ответ,
который не заканчивается. Серверу не нужна библиотека WebSocket (её нет в поставке, а скрипты выкатки зависимости
не ставят), nginx и прокси пропускают поток как обычный запрос. От браузера к серверу — обычные запросы
(`POST /api/v1/live/presence`). Браузер читает поток через `fetch`, а не `EventSource`: тот не передаёт заголовок
`Authorization`.

| Событие | Когда | Данные |
|---|---|---|
| `hello` | сразу после подключения | кто на карте, версия данных |
| `presence` | изменился список (проверка раз в 6 с) | вкладки: пользователь, центр и масштаб вида, объект правки |
| `network.changed` | новые строки `audit_log` (проверка раз в 2 с) | таблица, автор, число объектов, их id (до 50), охват на карте (участки, узлы), «мимо веба» |
| `data_version` | изменилась версия данных базы | версия — веб сразу берёт тайлы по новому адресу |
| `resync` | браузер не успевал читать | переподключиться |

Сервер закрывает поток через 10 минут, браузер сразу переподключается — вход проверяется заново (заблокированный
пользователь или истёкший токен поток не продлят). При обрыве — переподключение через 2, 4, 8 … 30 с; пока потока
нет, тайлы обновляет прежний опрос версии данных раз в 30 с.

**Правки — из `audit_log`.** Его пишут триггеры базы, поэтому видны и правки из десктопа. Триггер записывает роль
базы (`postgres`), API — пользователя веба в строке той же группы (`change_group_id`): автор правки берётся из неё.
Правка без строки API — «десктоп (postgres)». Рассылаются только таблицы сети и журналов (участки, узлы,
потребители, источники, насосные, регуляторы, задвижки, дефекты, шурфы, ремонты, опрессовки, осмотры); учётные
записи и служебные — нет. Старые значения полей не рассылаются — только какие объекты изменены.

**Присутствие.** Вкладка раз в 20 с сообщает центр и масштаб карты и открытую на правку карточку
(`tgid_live_presence`, UNLOGGED). Через 60 с без отметки человек считается ушедшим; при закрытии вкладки она
удаляется сразу. Ключ вкладки другим не показывается (вместо него — хеш): писать за чужую вкладку нельзя.

**Нагрузка.** Каждый процесс API опрашивает базу города сам — один раз на все свои открытые карты: раз в 2 с
`audit_log` после курсора (по первичному ключу) и версия данных, раз в 6 с присутствие. Пока карт не открыто,
опроса нет. Соединение с базой берётся только на время опроса. Поток в журнал действий не пишется.

## Адреса API

| Адрес | Кто | Что |
|---|---|---|
| `GET /api/v1/live/stream` | вошедший | поток событий (`text/event-stream`) |
| `POST /api/v1/live/presence` | вошедший | `{session_id, center: [lon, lat], zoom, editing: {kind, id, label} \| null}` → `{key}` |
| `DELETE /api/v1/live/presence/{session_id}` | вошедший | вкладка закрыта |

## Выкатка

- nginx: поток отдаётся с заголовком `X-Accel-Buffering: no` — nginx не копит его в буфере, отдельная настройка
  не нужна. Если для API включено `gzip` с `text/event-stream` в `gzip_types` — исключите этот тип.
  `proxy_read_timeout` — не меньше 30 с (по умолчанию 60 с; сервер шлёт пустой комментарий раз в 15 с).
- Каждая открытая карта держит одно HTTP-соединение с API. Uvicorn держит тысячи таких соединений; ограничение —
  500 потоков на процесс (503 сверх него).

## Проверено (копия Алматы, 31.10.2026)

- Поток curl: `hello` с присутствием; правка узла прямо в базе → `network.changed` («postgres», охват) и
  `data_version` за 2–4 с; правки API приписаны пользователю веба (`dev`), а не роли базы.
- Браузер: вкладка подключилась, вторая вкладка (с правкой карточки узла) — в меню «Сейчас на карте: dev — правит:
  карточка узла 535317»; правка узла в базе → уведомление «Изменения на карте — десктоп (postgres): узлы — 1»,
  новая версия тайлов, правка в «Последних правках» с «Показать на карте».
- Найдено и исправлено при проверке: первый проход рассылал вчерашнюю историю (нет «пола» курсора); после перерыва
  без открытых карт накопленное разослалось бы первому вернувшемуся; одна правка шла дважды — от роли базы и от
  пользователя веба.
- Не проверено в браузере: предупреждения в самой карточке правки (логика — тестами), работа за nginx.
