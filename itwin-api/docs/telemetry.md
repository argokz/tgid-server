# Телеметрия: факт против модели

Фаза 3 плана модернизации («Цифровой двойник»), шаг 1. Датчики давления, температуры и расхода привязываются к
узлам и участкам сети; их показания сравниваются с последним гидравлическим расчётом: где модель расходится с
жизнью — там ошибка в данных сети (диаметр, шероховатость, закрытая задвижка) или реальная проблема (засор,
утечка, неисправный регулятор).

- **Реестр датчиков** — «Расчёты и диагностика → Телеметрия: факт против модели»: код в SCADA / ОДПУ, что
  измеряет, подача или обратка, единица, узел или участок.
- **Показания** приходят от шлюза SCADA пачками (`POST /api/v2/telemetry/readings` по ключу API) или загружаются
  файлом выгрузки ОДПУ (CSV или Excel).
- **Сравнение**: последнее показание против значения модели в той же точке, оценка «норма / внимание /
  расхождение», «молчит» — нет свежих показаний; график за сутки, неделю или месяц с линией модели; датчики на
  карте цветом оценки.

Код:
- API: `database/telemetry.py`, `database/calibration.py`, `routers/telemetry.py`, миграция `sql/migrations/20261031_telemetry.sql` (API
  применяет её сам — `city_schema`), тесты `tests/test_telemetry.py`;
- веб: `components/TelemetryDialog.vue`, `utils/telemetry.ts` (оценки, график, тревоги), `services/api/telemetry.ts`,
  слой датчиков — `components/MapViewer.vue`, факт на пьезометре — `components/PiezometerModal.vue`, тесты
  `tests/utils/telemetry.spec.ts`.

## С чем сравнивается

Модель — последний расчёт фрагмента, где стоит датчик (`calculation` с наибольшим id для `fileid` узла или участка):

| Датчик | Где | Значение модели | Единица сравнения |
|---|---|---|---|
| Давление | узел | напор над отметкой трубы (`us_out.pih`; подача — `externalsign = 1`, обратка — 2) | м вод. ст. |
| Температура | узел | температура сетевой воды (`us_out.t`) | °C |
| Расход | участок | расход по модулю (`ut_out.a13`; подача — `externalsignlineid = 2`, обратка — 3) | т/ч |

Показания хранятся в единицах датчика и пересчитываются для сравнения: кгс/см² × 10, бар × 10,197, МПа × 101,97,
кПа × 0,10197, м вод. ст. × 1; м³/ч × 0,975 (плотность сетевой воды при 70–90 °C) → т/ч. Манометр должен
показывать избыточное давление на уровне верха трубы — как модель.

Оценка: давление и расход — расхождение до 5 % «норма», до 10 % «внимание», больше — «расхождение»; температура —
до 2 °C, до 5 °C, больше. «Молчит» — последнее показание старше 60 минут (`TELEMETRY_STALE_MIN`). Пороги — в
`database/telemetry.py` (`OK_PCT`, `WARN_PCT`, `OK_DEG`, `WARN_DEG`, `STALE_MIN`).

Поля десктопа «измеренное давление» узла (`nodes.calcpressflow` / `calcpressret`, пьезометр) не трогаются:
телеметрия хранит ряд показаний отдельно.

## Как приходят показания

**Шлюз SCADA** — `POST /api/v2/telemetry/readings` с ключом API пользователя с правом «Журналы» (заведите
отдельного пользователя для шлюза; ключ — «Учётная запись → Ключ API v2»):

```json
{"readings": [{"sensor": "PT-101", "ts": "2026-10-31T10:00:00+05:00", "value": 6.2}]}
```

До 10 000 показаний за запрос. Время без пояса — местное время сервера. Повтор того же времени датчика заменяет
значение (повторная отправка не дублирует); два значения на одно время в одной пачке — берётся последнее.
Неизвестные или выключенные коды и время из будущего (больше суток вперёд) пропускаются — ответ их перечисляет:
`{"accepted", "skipped", "unknown_codes", "future"}`. Приём в журнал действий не пишется (шлюз шлёт каждую минуту).

**Выгрузка ОДПУ** — «Загрузить выгрузку ОДПУ» в окне (право «Журналы»), CSV (UTF-8 или Windows-1251, разделитель
`;`, `,` или табуляция) или Excel, до 20 МБ:
- «длинный» вид — колонки `время`, `код`, `значение` (или `time`, `code`, `value`);
- «широкий» вид, как выгружают вычислители, — первая колонка время, остальные — коды датчиков.

Время — `ДД.ММ.ГГГГ ЧЧ:ММ[:СС]`, ISO 8601 или дата Excel; числа — с точкой или запятой.

**OPC UA** — шлюз ТГИД `scripts/telemetry/opcua_gateway.py` (ниже). **MQTT, Modbus** — шлюз протокола (Telegraf,
Node-RED, свой сервис) собирает показания и отправляет их пачкой в тот же `/api/v2/telemetry/readings`.

## Шлюз OPC UA и имитатор SCADA

`scripts/telemetry/` — отдельный инструмент, ставится на машину со связью и со SCADA, и с ТГИД (у SCADA обычно
отдельная сеть). Зависимость — `asyncua` (`requirements-telemetry.txt`, LGPL-3.0, в API не подключается):

    python -m venv .venv-telemetry
    .venv-telemetry\Scripts\pip install -r scripts/telemetry/requirements-telemetry.txt
    set TGID_API_KEY=<ключ API пользователя с правом «Журналы»>
    .venv-telemetry\Scripts\python scripts/telemetry/opcua_gateway.py gateway.json

- **`opcua_gateway.py`** — раз в `interval_s` читает теги сервера OPC UA (`tags`: узел OPC UA → код датчика в
  реестре ТГИД), значения с плохим качеством (датчик без связи) не отправляет — в ТГИД он станет «молчит»; время —
  метка источника. Нет связи с ТГИД — пачки копятся в `buffer_dir` (до 2000, по пачке на интервал — больше суток) и
  уходят по порядку, когда связь вернулась. Отказ 4xx (неверный ключ, данные) — пачка не повторяется, ошибка в
  журнале. Шифрование и вход OPC UA — `security`, `username`, пароль в переменной окружения. Служба Windows —
  через NSSM, как службы API. Пример — `gateway.example.json`.
- **`scada_emulator.py`** — имитатор SCADA для стенда и показа заказчику, пока нет доступа к настоящей: сервер
  OPC UA с тегами, значение = база × суточный ход + шум, сбои по расписанию — `drift` (засор, утечка: значение ×
  factor с минуты after_min) и `dropout` (каждые every_min минут на for_min минут плохое качество). Пример —
  `emulator.example.json` (пилот Алматы ниже).

На стенде «молчит» наступает через `TELEMETRY_STALE_MIN` минут (переменная API, по умолчанию 60).

## Хранение

`tgid_sensor_reading` (датчик, время) → значение, первичный ключ (датчик, время) и BRIN по времени — быстро и на
десятках миллионов строк (датчик раз в минуту — 0,5 млн строк в год). Если на сервере базы установлен
**TimescaleDB**, миграция сама превращает таблицу в гипертаблицу; сжатие и удаление старых показаний тогда
настраивает служба (`add_compression_policy`, `add_retention_policy`). Без TimescaleDB всё работает так же.

График — средние, минимум и максимум по интервалам (`date_bin`, до 500 точек: сутки — по 5 мин, месяц — по 3 ч).

## Тревоги (шаг 2, 30.10.2026)

Раз в минуту фоновая задача API (та же, что собирает события вебхуков, `database/webhooks.py`, под своим
advisory-замком) сверяет состояние каждого действующего датчика с прошлым: `bad` — расхождение с моделью,
`silent` — молчит, `normal` — норма или «внимание». Переход — тревога (`tgid_sensor_alert`, миграция
`sql/migrations/20261031_telemetry_alerts.sql`): что случилось, показание и модель в тот момент. Первая оценка
датчика тревоги не даёт (только запоминается), датчик без расчёта состояние не меняет. Тревога сразу становится
событием для внешних систем — `sensor.deviation`, `sensor.silent`, `sensor.recovered` (вебхуки и лента
`/api/v2/events`, см. `docs/webhooks-api-v2.md`). При `WEBHOOK_POLL_S=0` тревоги тоже выключены.

В окне «Телеметрия» — непринятые тревоги («расхождение», «молчит») с кнопкой «Принято» (право «Журналы»).

| Адрес | Кто | Что |
|---|---|---|
| `GET /api/v1/telemetry/alerts?open=&limit=` | вошедший | тревоги, новые первыми; `open=true` — непринятые «расхождение» и «молчит» |
| `POST /api/v1/telemetry/alerts/{id}/ack` | право «Журналы» | «принято»: кто и когда |

## Факт на пьезометре (шаг 2)

Пьезометрический график (`/piezometer/path`, `/piezometer/route`) отдаёт у узлов с датчиками давления `h_pod_fact`
/ `h_obr_fact` — напор по последнему показанию: отметка верха трубы + давление в м вод. ст., как расчётный напор
`h_pod` / `h_obr`; `t_pod_fact` / `t_obr_fact` — температура, `fact_at` и `fact_stale` — время показания и «молчит».
Окно пьезометра рисует их ромбами «H под (датчик)» и «H обр (датчик)» поверх расчётных линий. Поля десктопа
`h_pod_meas` (измеренное давление узла в базе) — отдельно, как и раньше.

Проверено на копии Алматы: маршрут 56 узлов от 2-36 до 7-10 — у 2-36 напор подачи по датчику 881,0 м против
расчётных 865,3 м (11,85 кгс/см² × 10 + 762,5), обратки 815,0 против 814,8; у 7-10 — 867,1 м. Тревоги: после
первой оценки (без тревог) показания изменены — давление подачи +15,3 % → «расхождение», обратка и молчавший датчик
→ «вернулся в норму»; три события `sensor.*` в ленте; «Принято» в окне. Тестовые данные удалены.

## Пилот на стенде: Алматы, имитатор SCADA (30.10.2026)

Доступа к настоящей SCADA нет — цепочка собрана целиком, как на проде, с имитатором вместо SCADA:
**имитатор SCADA (сервер OPC UA, `scada_emulator.py`) → шлюз (`opcua_gateway.py`) → ТГИД
(`/api/v2/telemetry/readings`)**. Копия Алматы, магистраль ТЭЦ-1 → 7-10 (9,4 км, 97 узлов), расчёт №710:

| Точка | Датчики |
|---|---|
| ТЭЦ-1 (узел 535303) | давление и температура подачи и обратки; расход подачи и обратки на выходе (участок 324808) |
| 2-20, 2-40А, 7-31, 7-10 | давление подачи и обратки |

14 датчиков (код `ALM-…`, имя «Н-ТЕСТ пилот …»), база имитатора — значения модели с отклонением прибора до 1,5 %,
суточный ход ±1,5 %, шум 0,4 %. Сбои: 7-31 подача — «засор» −12 % через 10 мин; 7-10 — связь пропадает на 5 мин
каждые 20 мин. Шлюз — раз в 30 с, на стенде `TELEMETRY_STALE_MIN=3`.

Что получилось:
- первая пачка — через 8 с после запуска шлюза, дальше по 14 показаний раз в 30 с;
- **итог фазы (5 точек, расхождение по давлению ≤ 5 %)**: 10 датчиков давления в 5 точках — 9 в пределах ±2,2 %,
  десятый — заложенный «засор» (−11,5 %) — пойман;
- тревоги: 7-10 «молчит» через 3 мин после пропадания связи (оба датчика), «вернулся в норму» после
  возвращения, 7-31 «расхождение −11,5 %» через минуту после «засора»; события `sensor.*` — в ленте API v2;
- ТГИД остановлен на 1,5 мин — шлюз сложил 3 пачки в буфер и отправил их по порядку после запуска: в ряду показаний
  нет пропусков (шаг 30 с);
- окно «Телеметрия»: 14 датчиков, 13 в норме, тревога по 7-31 с графиком падения давления; тревоги «молчит»,
  перекрытые возвратом в норму, из непринятых уходят сами.

Найдено при пилоте и исправлено: имена файлов буфера шлюза совпадали на Windows (грубый `time_ns`) — пачка
затирала пачку; тревога «молчит» висела после возврата датчика; длинные имена выталкивали колонки таблицы.

Это проверка цепочки и логики, а не модели: имитатор строит значения от самого расчёта. Настоящая проверка
расхождения «модель — факт» — на данных SCADA или ОДПУ города.

## Калибровка (шаг 4)

«Телеметрия → Калибровка» (`GET /api/v1/telemetry/calibration`, `database/calibration.py`): потери напора между
соседними датчиками давления одной трубы — по показаниям и по модели.

- **Пары** — датчики одной трубы, кратчайший путь между которыми по сети (граф пьезометра) не проходит через третий
  датчик. Направление — от большего напора модели к меньшему. Пары, путь которых идёт через насосную станцию, и
  пары с потерями модели меньше 1 м не сравниваются (список «Не сравниваются»).
- **Факт** — среднее за 30 мин (`TELEMETRY_CAL_WINDOW_MIN`) у каждого датчика: H = отметка + давление в м вод. ст.
  **Модель** — H = отметка + напор над отметкой последнего расчёта фрагмента.
- **Отношение r = ΔH факт / ΔH модели** и **погрешность**: два датчика по ±0,5 м вод. ст.
  (`TELEMETRY_PRESSURE_ACCURACY_M`) дают ±0,7 м на разность; на участке с потерями 5 м это ±14 % отношения.
- **Вывод**: «согласовано» (|r − 1| ≤ 10 %); «в погрешности» (в пределах двух погрешностей — сначала поверка
  манометров, модель не трогать); «шероховатость» (0,5…1,5 — эквивалентная шероховатость участков пары × r⁴: при
  том же расходе ΔH ∝ λ, λ ∝ k^0,25 по Шифринсону; предложение — в пределах 0,05…5 мм); «местное сопротивление»
  (r > 1,5 — шероховатостью не объяснить: прикрытая задвижка, засор, меньший диаметр); «проверить датчики»
  (r < 0,5).
- Модель не меняется: участки пары — на карте («Показать»), предлагаемая шероховатость — для проверки инженером
  (групповые установщики, сценарий «что если» с пересчётом). Расход, отличный от модели, даёт то же, что
  шероховатость (ΔH ∝ G²) — если на паре есть расходомер, сначала сверьте расход.

Пилот на стенде: пары 2-20 → 2-40А, 7-10 → 7-31 (подача; на 7-31 — «засор» имитатора), 7-31 → 2-40А,
2-40А → 2-20, 7-31 → 7-10 (обратка); ТЭЦ-1 → 2-20 не сравнивается — по пути насосная станция. «Засор» на 7-31
виден как r = 1,26 на паре 7-10 → 7-31 (потери 16,75 м против 13,29 м). Смещения приборов имитатора (до 1,5 %) на
коротких парах дают «в погрешности» — без учёта погрешности калибровка «лечила» бы шероховатостью ошибку манометра.
Отличить засор в одной точке от отложений по всей паре по двум датчикам нельзя — нужен датчик посередине.

Попутно: слои окон на карте (`useOverlayLayer`) больше не падают, если стиль карты ещё грузится (смена подложки,
первая загрузка), — рисуются, когда карта загрузится.
