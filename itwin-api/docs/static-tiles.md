# Статичные слои в PMTiles

Большой редко меняющийся слой (здания) запекается один раз в архив
[PMTiles v3](https://github.com/protomaps/PMTiles): карта берёт его тайлы из API готовыми, а не строит каждый
заново в базе (GeoServer или martin). Тот же файл — основа офлайн-подложек полевого приложения (фаза 2).

Код: `database/pmtiles.py` (формат: запись и чтение, без сторонних библиотек), `database/static_tiles.py`
(запекание и список архивов), задача воркера `bake_static_tiles` (`worker.py`), `routers/static_tiles.py`.
Веб: `utils/staticTiles.ts` (подмена адреса тайлов слоя), окно «Администрирование → Статичные слои (PMTiles)».
Тесты — `tests/test_static_tiles.py`, `tests/utils/staticTiles.spec.ts`.

## Что запекается

- Источник — функция тайлов martin `tgid_mvt_<слой>` в базе города (`scripts/martin`, возвращает API через
  `city_schema`): тайлы архива те же, что у martin, и подходят к стилю слоя GeoServer.
- Только слои без параметров SQL-представления (в функции — «у слоя нет параметров»): здания `zdaniya_2`,
  `zdaniya_tu`. Тайлы слоёв сети зависят от фрагментов и подписей — их не запечь.
- Зумы — с того, с которого слой виден (из комментария функции, у зданий 14), до 16 (можно до 18); выше
  верхнего MapLibre растягивает тайлы. Обход по дереву тайлов: дочерние — только у непустых; охват — таблица
  слоя и сеть города с запасом 0,05°. Тайлы — MVT в gzip, одинаковые хранятся один раз.

## Адреса

| Запрос | Что | Право |
|---|---|---|
| `GET /api/v1/static-tiles` | архивы города (зумы, тайлы, размер, когда собран, версия) и слои для запекания | вход (слои — админ) |
| `POST /api/v1/static-tiles/{слой}/build` `{maxzoom, minzoom?}` | запечь (Celery; ход — `GET /api/v1/task/{id}`) | админ |
| `DELETE /api/v1/static-tiles/{слой}` | удалить архив — слой снова из GeoServer или martin | админ |
| `GET /api/v1/static-tiles/{слой}/{z}/{x}/{y}.mvt?v=<версия>` | тайл (`Content-Encoding: gzip`); нет тайла — 204 | вход |
| `GET /api/v1/static-tiles/{слой}.pmtiles` | архив целиком, поддерживает `Range` | вход |

Веб при загрузке слоёв спрашивает список архивов и у MVT-слоя той же рабочей области, что слой участков,
подменяет адрес тайлов на API (с токеном — `mapStore.transformRequest`), зумы источника и охват. Версия
архива в адресе: пересобранный архив — новые адреса мимо кеша браузера (тайлы кешируются на 7 дней).

## Хранение

`STATIC_TILES_DIR` (по умолчанию `files/static_tiles` в каталоге API), внутри — каталог города
(`almaty/zdaniya_2.pmtiles`). API и воркер должны видеть один каталог (на одном сервере — по умолчанию так).
Архив пишется во временный файл и заменяется целиком: читатели не видят полузаписанный.
`STATIC_TILES_QUEUE` — очередь задачи запекания (по умолчанию основная; в API на несколько городов —
очередь города).

## Замеры (копия Алматы, 29.10.2026)

- Здания `zdaniya_2` (187 тыс. контуров): 3120 тайлов z14–16, архив 21 МБ, запекание 48 с (4 соединения).
- Тайл из архива — 7–10 мс; тот же тайл из базы — 50 мс (z15) … 0,4 с (плотный z14) даже с индексом.
- У `zdaniya_2` не было пространственного индекса: тайл из базы строился полным проходом (0,15–0,6 с).
  Индекс теперь создаёт `city_schema` («пространственные индексы зданий»,
  `sql/migrations/20261029_buildings_gist.sql`) — быстрее стали и GeoServer, и martin.
- После правки зданий в десктопе или вебе архив нужно пересобрать (окно администратора — «Пересобрать»).
