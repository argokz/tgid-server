# Один API на все города

С 29.10.2026 (фаза 1 модернизации) один процесс API и общие воркеры Celery могут обслуживать все
города вместо отдельных служб API и воркера на каждый город (сейчас их 24, плюс 12 баз Redis).

## Как включается

Переменная `TGID_CITY_DBS` — список `код=база` через запятую:

```
TGID_CITY_DBS=almaty=almatygid,astana=astanagid_2026_09_22,shatura=shatura
```

Без неё API работает как раньше: один город, база `DB_NAME`, город — `TGID_CITY` или по имени базы.

## Город запроса

- Путь API начинается с `/city/<код>/`: `/city/astana/api/v1/...`. Middleware `city_context.py` снимает
  префикс и запоминает город запроса (`cities.current_city()`); маршруты, ссылки и проверки путей
  остаются прежними.
- nginx: `location ^~ /tgid/<код>/map-api/ { proxy_pass http://127.0.0.1:8060/city/<код>/; }` — веб и
  его `NUXT_PUBLIC_MAP_API_BASE_URL` не меняются.
- Без префикса отвечают только `/health`, `/metrics` и `/auth/check` (проверка входа GeoServer, город там
  определяется по рабочей области). Остальное — 404 «Город не указан». Неизвестный город — 404.
- `/health` без префикса проверяет базы всех городов (`database.cities`, `city_schema.cities`),
  `/city/<код>/health` — базу одного города.
- Доступ пользователя к городу проверяется как раньше (`users.cities`): по городу запроса.

## Что разделено по городам

| Что | Где | Как |
|---|---|---|
| Пул соединений | `database/connect.py` | `city_pools[код]`; открывается при запуске, недоступная база — при первом запросе |
| Подключение для psycopg2 и проверки пароля | `cities.city_db_name()` | база города запроса |
| SRID сети, колонка `internalnodeid` | `database/net_srid.py` | по городу |
| Кеши каталога, графов, колонок журнала, версии данных, охвата OGC | `cities.cache_key()` | ключ — код города (у API одного города — `''`) |
| Доводка базы (`city_schema`) | `main.py`, `database/city_schema.py` | своя фоновая задача и своё состояние на каждый город |
| Функции тайлов martin | `MARTIN_SQL_DIR/<город>.sql` | вместо `MARTIN_SQL_FILE` одного города |
| Метрики | `observability.py` | метки `city` у пула и схемы; длина очереди — сумма очередей городов |

## Задачи Celery

- API кладёт задачу в очередь города `tgid.<код>` (выгрузки с `FILE_JOBS_QUEUE` — `<очередь>.<код>`) и
  ставит заголовок `tgid_city`.
- Воркер перед задачей берёт город из заголовка (`task_prerun`), база — `city_db_name()`: расчёт sety
  (`-database`), теплопотери, износ, выгрузки. Задача без известного города не выполняется (ошибка, а не
  чужая база).
- Воркер слушает очереди своих городов: общий — все (`-Q tgid.almaty,tgid.astana,...`), для крупного
  города можно поставить отдельный (`-Q tgid.almaty`).
- Redis — одна БД на все города: очереди у городов свои, ключи результатов и файлов — по id задачи.
  Общий API может работать в той же БД Redis, что и прежний API города: его воркеры слушают очередь
  `celery`, задачи `tgid.*` они не заберут.

## Безопасность

Токен входа общий для всех городов, поэтому доступ к городу проверяется на каждом запросе:
- `AuthRequiredGetMiddleware` (main.py) после проверки подписи делает живую сверку
  (`apply_live_user_status`): блокировка и `users.cities` — для всех маршрутов, в том числе без
  зависимости `get_current_user` (карточки `/line`, `/node`, `/lookup`, `/task`). Это закрывает и прежнюю
  дыру отдельных API городов: токен Алматы открывал такие маршруты API Астаны.
- Город, которого нет в справочнике `TGID_CITIES`, в режиме нескольких городов открыт только
  пользователям «все города».
- Статус роли PostgreSQL (`AUTH_BACKEND=pg`) кешируется по городу: роль читается из базы города.
- Статус, результат и файл задачи Celery отдаются только запросу того же города
  (`tgid:task-city:<id>` в Redis, ставится при публикации задачи).

Известное ограничение: `/auth/check` вызывается без города. Для ролей PostgreSQL сверка статуса там не
выбирает базу и, как при недоступной базе, доверяет токену. Пока проверку входа GeoServer выполняет API
Алматы (nginx `tgid_auth_api`), это не действует.

## Установка на сервере

`H:\deploy\install-tgid-multicity.cmd` (запускает `scripts/multicity/install-multicity.ps1`), после
обновления кода API:

1. предпроверки: код, базы городов, лимит соединений PostgreSQL, порт 8060, `nginx -t`;
2. службы `tgid-api-multi` (2 процесса uvicorn, пул на город 1–6 соединений) и `tgid-worker-multi-1/2`;
3. проверка: `/health` по всем базам, `/fragments` каждого города — как у прежнего API;
4. nginx: map-api городов → общий API (бэкап, `nginx -t`, reload).

Прежние службы городов не удаляются. Откат — `install-multicity.ps1 -Disable`. Часть городов —
`-Only almaty,astana`.
