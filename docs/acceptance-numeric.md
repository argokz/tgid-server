# Численная приёмка расчёта sety: веб = десктоп

Даты: 2026-09-26 — 2026-09-28. База: копия `almatygid_copy` (дамп прода от 2026-09-25 12:37).
Инструмент: `itwin-api/scripts/golden/compare_calc.py`. Он сравнивает два расчёта строка к строке:
`ut_out` по ключу (участок, признак трубы), `us_out` по ключу (узел, признак), `pt_out` по ключу
(узел, источник). Допуски заданы по колонкам: значение проходит, если |Δ| ≤ abs или |Δ|/|эталон| ≤ 0.1 %.
В отчёт попадают max и средний |Δ|, max относительный Δ, число значений вне допуска и 20 худших
строк по превышению допуска.

```
cd itwin-api/itwin-api
./venv/Scripts/python.exe scripts/golden/compare_calc.py --base <эталон> --new <кандидат> --out report.md
```
Скрипт подключается по `.env` и `.env.copy` (копия БД), флаг `--no-copy` отключает `.env.copy`.
Работает только на чтение. Код возврата 0 означает, что всё в допуске.

## Командная строка десктопа (gid8 `gidview/gidr_calc.cpp`, `getDoItDr`, плановый режим)

```
python <exe>/sety/ww.pyc -type_of_net 1 -server … -database … -user … -port … -fileID <id>
  [-dross_yes] [-avtomat_yes] -iter <N> -dross -Tn <T> -tp_metod <M> -trtp <K>
  -sopr <0..4> -roP <ρп> -roO <ρо> [-ro_temp] -rdbms postgreSQL -out_file … -password …
  [-zulu_zn0] [-zulu_utechki] [-char_sety] [-no_teplovyd] [-uf_calc] [-tg [-no_teplopoter]]
  -time "…" [-name "…"] [-mag_fragment] [-veter] [-save_po] [-no_kv] -user_gid "…"
```
- Первым ищется собранный `sety/ww.pyc` рядом с exe, и только потом исходники `python/sety/sety/ww.py`.
- `M` — индекс `combo_Metod`. В списке один пункт («нормы»), поэтому всегда передаётся `-tp_metod 0`.
  У sety по умолчанию 1. Движок этот параметр не использует (`teplo/y_ut.py`, код закомментирован).
  Веб теперь тоже передаёт `-tp_metod 0`, чтобы `calc_params` совпадали.
- Поля `sopr`, `roP`, `roO`, `-no_kv` и `-uf_calc` в `calculation.calc_params` **не сохраняются**.
  Восстановить их по записи в БД нельзя.

### Почему `-save_po` обнулил нагрузки: так работает движок десктопа, веб здесь ни при чём

Проверено 27.09 без записи в БД: сессия `default_transaction_read_only=on`, остановка перед `w_out2.w_out`.
Фрагмент 3 («СЭР») с аргументами веба дал SQL, совпадающий со снимком «после» у всех 24 строк.
Исходники десктопа `gid8/python/sety` с его аргументами по умолчанию (`-tp_metod 0 -ro_temp`) дают
те же 62 кортежа VALUES байт в байт. SQL сохранён в cp1251 и прочитан верно, иначе кириллические
`kod`/`uzel` не сопоставились бы ни с одной строкой.
- `g2.make_G2` суммирует по каждому узлу с заданным напором (`setPressNodes.kod_m/uzel_m` → фрагмент 74)
  только узлы `typ == 'realConsumers'`. Во фрагменте 3 715 обобщённых потребителей и всего 11 реальных,
  поэтому `otopl_zco → calcHLdep`, `ventil_cv`, `gv_op` и остальные суммы равны 0. Для `cx_zco → connectionSchemeID`
  начальное значение 0, а `Tr_tv_co_zco → calcTempDep` всегда 18. Ненулевой остаётся только
  `normHLosFlow` (теплопотери участков).
- `3-ГР-21` фигурирует в VALUES дважды: два узла с заданным напором ссылаются на один узел магистрали.
  `UPDATE … FROM` при нескольких совпадениях применяет одну из строк, какую именно, не определено.
  На десктопе поведение то же.
- На десктопе флажок «Записать тепловые нагрузки в обобщённый потребитель» каждый раз открывается снятым
  (`m_bSave_po = false`). `-save_po` рассчитан на фрагменты, где потребители реальные. Если включить его
  для фрагмента из обобщённых потребителей, нагрузки магистрали затрутся и на десктопе.

## Отображение результатов (этап 5.4)

Проверено живыми запросами к API (новый код, `TestClient`, копия) против SQL по расчётам 2 и 9.
GeoJSON тематической карты: 1727 участков, из них 35 только с обраткой, и 1872 узла.
Excel результатов: 1727 строк. Пьезометр: маршрут из 40 узлов плюс его Excel.
После исправлений расхождений 0. Найдено и исправлено:

- **Напор обратки.** `sety/w_out.py` пишет в строки подачи и обратки одинаковые `a19` (напор
  **подачи** в конечном узле) и `a18` (подача минус обратка). Поэтому Excel в колонке «Пьез. напор в
  конце обр.» и карта для участков только с обраткой показывали напор подачи. Правильно
  брать `a19 − a18`. Проверено на SQL: `a19 = us_out.pih(подача)` у 1614 из 1692 строк подачи и у
  1611 из 1674 строк обратки, `a19 − a18 = us_out.pih(обратка)` у 1612.
  Располагаемый напор участка без подачи теперь берётся из строки обратки.
- **Пьезометр показывал измеренное давление вместо расчётного.** `nodes.calcpressflow/ret` в
  gid8 означают «Измеренное давление», по умолчанию 0. Пьезометр ставил их выше `us_out`. У 497
  из 498 узлов фрагмента 74 там 0, и график ложился на отметку земли (сервер 8040:
  `h_pod = h_obr = z = 799.2` у узлов 537880/536319 при расчётном `pih = 62.17`). Теперь напоры
  берутся ровно из `us_out`, а измеренные отдаются отдельно (`h_pod_meas`/`h_obr_meas`, только ненулевые).
- **Пьезометр смешивал расчёты.** Для каждого узла и участка брался свой последний
  расчёт, а `pt_out` соединялся без `calculationid`, поэтому на один узел приходилось по строке на
  каждый расчёт. Теперь весь маршрут строится по одному расчёту: `calculation_id` из запроса
  или последний, в котором есть узлы маршрута. Номер расчёта возвращается в ответе.

## Формулы без БД (этап 5.5, `tests/golden/`)

`tests/golden/test_desktop_formulas.py` считает эталон исходниками десктопа из `gid8` в отдельном
процессе (`import sety` там — пакет gid8). Без каталога `gid8` тест пропускается.
- элеватор: `drsh2` на 163 наборах G × u × h_c × H, включая пример G=10, u=1.4, h_c=1.5,
  H=20 → горловина 37.6 мм, №6. Горловина вычисляется выражением `dg`, взятым из исходника `drsh2`;
- шайба движка: `drsh1`/`drsh3` на 35 наборах G × H;
- бланк дроссельных устройств: формулы ячеек G17…G43 извлекаются из `gid8/python/dross/dross.py`
  и считаются интерпретатором IF/ROUND/POWER, 5 наборов нагрузок и напоров;
- график ОТОП: `tg1.CalculateOT1` на 6 графиках (срезки, uf, tn_5 = −32 / −25 / −21 / −20.1).

**Найдено и исправлено:** при срезке по температуре обратной воды (`t2_2r`) десктоп поднимает
t1 на 0.05 °C за проход без ограничения числа проходов, а веб останавливался через 80 проходов
(+4 °C). На графике 150/70 с tн = −32 и t2_2r = 40 веб давал t1 до 8.4 °C ниже десктопа, а t2
падал ниже срезки (36 °C вместо 40). Лимит поднят до 10 000 проходов, все 6 графиков совпадают в
пределах 0.05 °C (округление веба до 0.1).

**Особенность, оставлена:** при дробной tн_5 сетка точек разная. Десктоп (`tg_h.tg_range`) даёт
−20.1, −20, −19 … 8, веб даёт −20.1, −19.1 … 7.9 с шагом 1 °C. Интерполяция sety
(`read_tg.get_tg`) предполагает шаг 1 °C, поэтому сетка веба с движком согласована. Тест сверяет
значения в точках веба.
